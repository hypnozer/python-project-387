# План развития

План предназначен для отработки полного агентского цикла в GitHub: каждая
задача оформляется отдельным issue, проходит triage, реализуется агентом в
отдельном pull request и принимается после ревью. Задачи расположены в порядке
приоритета и достаточно независимы, чтобы не превращать учебный процесс в одну
большую продуктовую доработку.

## P0 — надёжность данных

### Баг: данные пропадают после перезапуска приложения

Сейчас форматы встреч и бронирования находятся только в памяти процесса. После
рестарта backend они исчезают, поэтому опубликованным приложением нельзя
пользоваться как постоянным календарём.

**Критерии готовности:**

- данные хранятся в PostgreSQL, а для локальной разработки поддерживается
  документированный запуск базы;
- схема создаётся миграциями;
- после перезапуска backend созданные форматы и бронирования сохраняются;
- конкурентные запросы не могут забронировать один слот дважды;
- интеграционные тесты проверяют сохранность и защиту от двойной записи.

### Баг: кабинет владельца доступен любому посетителю

Маршрут `/owner` и административные API сейчас не защищены. Любой пользователь
может увидеть email гостей и создать новый формат встречи.

**Критерии готовности:**

- административная страница и `/owner/*` требуют авторизацию;
- создание и изменение форматов встреч недоступно гостю;
- публичный список форматов и бронирование остаются доступны без входа;
- тесты покрывают ответы `401` и успешный авторизованный сценарий;
- секреты передаются через переменные окружения и не попадают в репозиторий.

## P1 — основные пользовательские сценарии

### Фича: отмена бронирования гостем

Добавить в подтверждение встречи безопасную ссылку с одноразовым токеном. После
отмены слот снова должен появляться в выдаче доступного времени.

**Критерии готовности:**

- контракт содержит получение бронирования по токену и его отмену;
- повторная отмена обрабатывается идемпотентно;
- токен нельзя подобрать по идентификатору бронирования;
- frontend показывает отдельные состояния успеха, уже отменённой и не найденной
  встречи;
- API- и e2e-тесты покрывают основной сценарий.

### Фича: редактирование и архивирование форматов встреч

Владелец может исправить название, описание и длительность формата, а также
скрыть его с публичной страницы без удаления существующих бронирований.

**Критерии готовности:**

- добавлены операции обновления и архивирования в TypeSpec/OpenAPI;
- архивный формат нельзя забронировать, но он виден в старых бронированиях;
- изменение длительности не меняет уже созданные встречи;
- интерфейс явно предупреждает о влиянии изменений;
- backend- и e2e-тесты проверяют оба сценария.

### Баг: устаревший ответ может перезаписать актуальные данные

Хук `useApiData` не отменяет предыдущий запрос. При быстрой навигации или
повторной загрузке более медленный старый запрос может завершиться последним и
показать данные другого формата встречи.

**Критерии готовности:**

- предыдущий запрос отменяется через `AbortController` либо его результат
  гарантированно игнорируется;
- после размонтирования компонента состояние не обновляется;
- тест воспроизводит ответы в обратном порядке и подтверждает показ актуальных
  данных;
- кнопка повторной загрузки сохраняет корректные состояния загрузки и ошибки.

## P2 — качество и удобство

### Фича: настройка доступности владельца

Вместо предопределённого расписания понедельник–пятница дать владельцу
возможность настраивать часовой пояс, рабочие интервалы и выходные дни.

**Критерии готовности:**

- интервалы одного дня валидируются и не пересекаются;
- смена часового пояса не изменяет абсолютное время существующих бронирований;
- генерация слотов корректна на границах перехода на летнее/зимнее время;
- настройки сохраняются и редактируются в кабинете владельца;
- добавлены модульные тесты для часовых поясов и граничных дат.

### Фича: email-уведомления и календарный файл

После бронирования отправлять гостю и владельцу подтверждение, а также давать
скачать событие в формате iCalendar (`.ics`).

**Критерии готовности:**

- отправка письма выполняется вне основного HTTP-запроса и может быть повторена;
- ошибка почтового провайдера не создаёт дубликат бронирования;
- `.ics` содержит корректные UTC-даты, часовой пояс и стабильный UID;
- шаблоны писем не раскрывают лишние персональные данные;
- интеграционные тесты используют тестовый транспорт без реальной отправки.

### Баг: недостаточно автоматических проверок frontend

Сейчас frontend проверяется сборкой и одним сквозным сценарием. Ошибки в
форматировании дат, состояниях загрузки и обработке API выявляются поздно.

**Критерии готовности:**

- настроены unit/component-тесты для форматирования дат, API-клиента и основных
  состояний страниц;
- в CI отдельно выполняются typecheck, unit-тесты и e2e;
- отчёт о покрытии публикуется вместе с backend-покрытием;
- нестабильные тесты не скрываются безусловными повторами.

## Процесс работы с агентом

1. Создать issue по одной задаче из плана и добавить ожидаемое поведение,
   ограничения и метки приоритета/типа.
2. Попросить агента провести triage: подтвердить проблему, обозначить затронутые
   компоненты, риски, тестовый план и критерии готовности.
3. После согласования анализа поручить агенту создать PR с минимальным набором
   связанных изменений.
4. Провести ревью, оставить конкретные замечания и поручить агенту доработать тот
   же PR.
5. Смержить PR только после успешных автоматических проверок.

Для первого полного цикла рекомендуется баг с устаревшими ответами
`useApiData`: он локален, воспроизводим тестом и подходит для содержательного
ревью без изменения продуктовой архитектуры.
